# Risk Matrix

These are the main risks considered for the automated tests of the MultiBank website. Some could make a test fail when the website is actually fine. Others could let a real problem slip through while every test passes. Likelihood and impact are my own judgement: High, Medium or Low.

| Risk | Likelihood | Impact | What we do about it |
|---|---|---|---|
| **Market data changes during a test.** The Explore page reloads its category lists about every five seconds and the ranking can change, so a comparison can fail even when the page is right. | High | Medium | The category test keeps the first market data response and serves it again when the page reloads. The other trading tests check value formats, never the values. |
| **Holding the data still hides a refresh problem.** Because the category test holds one response still, it would not notice if the table stopped updating. | Low | Medium | Only one request is held, and only in that test. The other trading tests run on live data. Checking that the table refreshes by itself is a known gap. |
| **Slow loading causes false failures.** During development the full Spot market table took 7–8 seconds to appear, and the error message only appears after the page retries a failed request (about 7 seconds). | Medium | Medium | Both waits allow up to 15 seconds, the same in every browser. If the site gets slower than that, the test fails and we report it rather than raise the limit. |
| **The live site changes or is unavailable.** New marketing copy, rotated promotions, an outage or bot protection can fail tests without a real bug. | Medium | Medium | Page text is checked with short key sentences, and copy that may change is kept in `test-data/`. The browsers use Playwright's desktop settings, so they don't announce themselves as headless. Screenshots and traces show whether the site or the test changed. |
| **External services change or slow down.** The app download link goes through Adjust, a third-party link service, and $MBG opens the separate token website. | Medium | Low | Only the first redirect of the app link is checked, and no store page is opened. The token site is checked by its URL only. In the broken-link check, each link gets 10 seconds. |
| **The visitor's location changes the site.** A run from outside the UAE may be served `/en/` instead of `/en-AE/`. | Medium | Medium | URL checks only look at the end of the path. Expected content was taken from the UAE site, so the first run from another region needs a careful look. |
| **Browsers behave differently.** WebKit was slower during development, and the menu briefly shows a fallback font before its web font loads, which moves the menu items for a moment. | Medium | Medium | Expectations and timeouts are the same in every browser. Menu positions are read in one go, so they always come from the same layout. A failure in one browser is reported, not hidden. |
| **Real problems sit outside what the suite checks.** Logged-in trading isn't tested, and some issues found while exploring (for example coin pages returning HTTP 500, or $0.00 prices when the price feed fails) have no automated test. | High | High | These issues are listed in the [release readiness checklist](release-readiness.md#known-issues-and-risks) so they get a decision before release. |
